## 四、存储与分类

### 4.1 列

在 `skills_evidence` 上增加：

| 列 | 类型 | 新行 | 旧行迁移 |
|---|---|---|---|
| `status` | `TEXT NOT NULL DEFAULT 'claim'` | `claim` 或 `verified` | 一律 `claim` |
| `issuer` | `TEXT NOT NULL DEFAULT 'guibu'` | 固定 `guibu` | `guibu` |
| `issued_at` | `TEXT` | `payload.generated_at`，缺则用写入时刻的 UTC ISO | 抄 `created_at` |
| `expires_at` | `TEXT` | 抄 `payload.expires_at`，没有则为 SQL `NULL` | 保持 `NULL`，不解析旧 payload |

`EvidenceStore.__init__` 在现有 `CREATE TABLE IF NOT EXISTS` 之后做迁移：用 `PRAGMA table_info(skills_evidence)` 看缺哪列，缺则 `ALTER TABLE ... ADD COLUMN`。已有新列的库再打开不得报错，也不得把旧行改成 `verified`。

SQLite 的 `ADD COLUMN ... NOT NULL` 必须带 `DEFAULT`。

### 4.2 发行方名单

`config.allowed_skill_issuers() -> set[str]`：

- 读环境变量 `ALLOWED_SKILL_ISSUERS`。
- 未设置时默认 `{"guibu"}`。
- 按逗号拆开，去掉空白，转小写。
- 设置为空字符串时得到空集合：任何行都不得标 `verified`，摄入仍成功，`status=claim`。

`.env.example` 增加：

```
# 允许把技能证据标为 verified 的发行方。逗号分隔，默认 guibu。
# 未出现在名单中的发行方只能留下 claim。S1 的摄入端点不读请求里的 issuer，固定记为 guibu。
# ALLOWED_SKILL_ISSUERS=guibu
```

### 4.3 写入时如何定 status

只在 `insert` 的新行上计算。`UNIQUE(signal_type, user_id_hash, nonce)` 命中时返回旧行，不重算 `status`。

`issuer` 固定为 `guibu`。不读 payload 里的发行方。

`verified` 当且仅当四项都成立：

1. HMAC 与持有人：沿用现有摄入路径。验签失败仍是 401，不落库。`user_id_hash` 与 `payload.user_id` 不一致仍是 422。dev 免签（未配置 `SIGNAL_BRIDGE_SECRET`）允许落库，不因此禁止 `claim`，也不因此禁止后面的背书判定。
2. 发行方：`"guibu"` 属于 `allowed_skill_issuers()`。
3. 背书：`payload.proofs` 中存在一项，`type` 去掉首尾空白后等于 `yedall_attestation`，且 `value` 去掉首尾空白后非空。
4. 过期：`expires_at` 缺省、`null` 或空字符串时，不因过期拒绝。有值且能解析成时间、并且该时间不晚于当前 UTC，则不得标 `verified`。无法解析的 `expires_at` 不拒绝摄入，该行不得标 `verified`。

四项任一不成立：`status=claim`，HTTP 仍是现有的 200。不新增 4xx。

### 4.4 读

删除「把全部摄入记录都叫已验证」的行为。`get_verified_skills` 不再返回未背书记录。实现时让它变成 `get_verified` 的别名，或改掉全部调用点。调用点今天有三处：`store.py` 自身、`src/tatha/jobs/pipeline.py`、`src/tatha/api/app.py` 的 `jobs_match`。

`get_verified(user_id_hash)`：只聚合 `status='verified'` 且读时未过期的行。过期规则与 4.3 第 4 项相同。读时过期的 `verified` 行不进入本函数。

`get_claims(user_id_hash)`：聚合 `status='claim'` 的行，加上读时已过期的 `verified` 行。技能若已出现在 `get_verified` 的结果里，从本函数的结果中去掉，避免同一技能两块都写。

两条的聚合形状保持今天 `get_verified_skills` 的元素形状：`{"skill", "evidence": [{source, excerpt, learned_at, file_path, start_sec, end_sec, similarity}]}`。

## 五、注入文案与接口

### 5.1 两段标题（逐字使用）

声明块，仅当 `get_claims` 非空：

```
## 学习记录（Guibu 微课，尚未第三方背书）
```

已验证块，仅当 `get_verified` 非空：

```
## 已验证技能（yedall_attestation 背书，非自述）
```

声明块的标题和条目里不得出现「已验证」三字。条目格式沿用现在的 `- {skill} — 证据 {n} 条：{source}「{excerpt}」`。

`enhance_resume` 改为接收两份列表。注入顺序：声明块在前，已验证块在后。两份都空时简历原文不变。`pipeline.py` 仍用今天的 `try/except`，增强失败不阻断匹配。

`build_evidence_block` 不再用单一的 `_HEADER`。按调用方传入的标题生成，避免声明路径复用含「已验证」的常量。

### 5.2 `POST /v1/jobs/match`

`JobMatchResponse`：

- `verified_skills`：`get_verified` 的结果。无背书时为 `[]`，不要返回 `null` 来表示「有声明」。传入了 `user_id_hash` 且存储可读时，两个列表都返回（可以是空列表）。未传 `user_id_hash` 时两个字段都为 `null`，与今天「未查询」一致。
- `claimed_skills`：`get_claims` 的结果，规则见 5.2 上一条。

`pipeline` 注入用的列表必须和响应里这两个字段是同一次读取的结果，避免响应写 `[]`、简历里却仍写着旧标题。

### 5.3 `POST /v1/skills/ingest`

响应增加 `credential_status`，取值为该行的 `status`（`claim` 或 `verified`）。幂等命中时返回库中已有值，不重算。

原字段 `verified` 保持 HMAC 语义：配置了密钥且验签通过为 `true`，dev 免签为 `false`。

### 5.4 文档

`docs/skill_evidence_ingest.md` 里「聚合全部证据，打已验证」的句子改成两态：无 `yedall_attestation` 只注入第六节里的声明标题；有未过期背书且发行方在名单内才注入已验证标题。删掉或改写「无证明 vs 有证明 → 技能命中率上升」作为本脚本唯一判据的写法。蒸馏对比可以保留为人工观察，不再作为「有摄入即已验证」的验收。

## 六、ADR（原文放进 Tatha）

新建 `docs/adr/0001-skill-credential-two-states.md`，正文如下，不要在 PR 里改角色名或两态的定义。

```markdown
# ADR 0001：技能凭证的四个角色与两态

## 状态

已接受。2026-10-10。适用于 GenzLTD/Tatha 的技能证据。S2（网关按路由鉴权）与 S3（三份 auth.py 收口）不在本决定里。

## 四个角色

- 发行方：出具技能学习证据的一方。S1 只有 Guibu，标识字符串 `guibu`。
- 持有人：证据所属的人。关联键是 `user_id_hash = sha256(email.lower().trim())`。邮箱与简历原文不出 Tatha。
- 核验方：决定匹配与简历增强能否把某项技能写成已验证的一方。S1 是 Tatha 自己的存储与 `resume_enhancer`。
- 信任登记：决定谁有资格发行技能证据，并在以后保存锚点的一方。S1 用 Tatha 配置 `ALLOWED_SKILL_ISSUERS` 暂代，默认只有 `guibu`。planetx 以后用数据表承担登记，不用 Solidity 合约。

## 两态

- `claim`：库里有一条摄入记录。它是学习材料，不是第三方认可。
- `verified`：该行同时满足背书、发行方名单、未过期。背书指 `proofs[]` 中存在 `type=yedall_attestation` 且 `value` 非空。

「已验证」三字只允许出现在 `verified` 的注入标题和对应 API 字段的说明里。`claim` 的注入标题是「学习记录（Guibu 微课，尚未第三方背书）」。

摄入响应里的 `verified` 布尔值只表示 HMAC 验签结果，不表示凭证状态。凭证状态字段名是 `credential_status`。

## 明确不做

不上主网。不把 planetx 做成第二套打分引擎。claw 停在草拟与人确认，不自动投递。S1 不回写锚点；锚点未到之前，`verified_skills` 为空是正确行为。
```

`test_store_get_verified_skills_aggregates`：`make_payload()` 的 `proofs` 为 `[]`。断言 `get_verified` 为空，`get_claims` 含「列表推导式」，行上 `status=claim`、`issuer=guibu`。

### 7.2 新增

| 用例 | 安排 | 断言 |
|---|---|---|
| 有摄入、无背书 | `proofs=[]`，走 `insert` 后 `enhance_resume` | 注入文本不含「已验证」；含声明标题 |
| 有背书且未过期 | `proofs=[{type:yedall_attestation, value:tx-1}]`，`expires_at` 为明天，名单含 `guibu` | `status=verified`；`get_verified` 含该技能；`get_claims` 不含该技能；文本含已验证标题 |
| 有背书但已过期 | 同上，`expires_at` 为昨天 | `status=claim`；文本不含「已验证」 |
| 无 `expires_at` 但有背书 | 不传 `expires_at` | 摄入 200；`status=verified` |
| 无 `expires_at` 且无背书 | 与今天的 `make_payload` 相同 | 摄入 200；`status=claim` |
| 发行方不在名单 | `monkeypatch.setenv("ALLOWED_SKILL_ISSUERS", "")` 后摄入带背书的载荷 | 摄入 200；`status=claim` |
| 无法解析的 `expires_at` | `expires_at="not-a-date"` 且带背书 | 摄入 200；`status=claim` |
| 幂等不升级 | 先以 `proofs=[]` 写入，再用同一 nonce 送带背书的载荷 | 仍是第一行；`status` 仍为 `claim` |
| 旧库迁移 | 用本 PR 之前的建表语句建库并插入一行，再用新 `EvidenceStore` 打开 | 新列存在；该行 `status=claim`；不被改成 `verified` |
| 同一技能两行 | 一行 `claim`、一行 `verified`，技能名相同 | 只出现在已验证块 |

## 九、待决项

⚠️ 待决项（建议在评审通过前落定）：S1 落地后 `verified_skills` 恒为空，根因是 `yedall_attestation` 尚无生产方签发——YEDALL 侧 `access_logs.result_status`（ok/denied/revoked）语义上最自然，但 `src/tatha/core/yedall_bridge.py` 当前是 YeDall↔Qiankun 计费桥（`check_scene_budget` / `record_scene`），签发路径不通。须先明确由 YEDALL 发、还是先做受控内部签发脚本把回路跑通，否则本施工单评审「通过」即带着此留白进实施，`verified_skills` 将恒空、简历里「已验证」彻底消失。

取证（2026-10-10）：`gh search/code yedall_attestation repo:GenzLTD/Tatha` 命中数为 0，即该背书类型当前在开发范围外不存在生产者；本施工单是它第一次出现在 Tatha 的规格里。

本事项不阻塞 S1 本身的合并——S1 的目的是停止把「摄入」误称为「已验证」，是否把 credential 真正推向 `verified` 取决于本节的答案。
